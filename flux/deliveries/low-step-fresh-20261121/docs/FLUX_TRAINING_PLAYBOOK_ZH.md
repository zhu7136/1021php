## 1. 本次必须纠正的结论

**“CLI 不支持上传本地 ZIP，所以必须让用户去网页上传 ZIP”是错误推论。**

原始手册 v0 §5.2 已记录成功实践的普通 Git 数据分片交付：分片随代码 clone 进入远端，
入口在本地校验和重组。它不依赖 `task storage upload`，也不要求每次让用户在网页上传 ZIP。
`flux task storage` 只有 `list`，不能编造上传子命令，但这不妨碍 Git 分片路径。

v4 §3.2 的 `input_archive` 私有本地文件默认值，描述的是那一次 **HU_D04 跑速恢复修复入口**，
不是所有 Flux 项目的唯一交付方法。Git 分片重组后同样能生成经过验证的本地输入包；
是否能直接接入原恢复入口，仍需适配其参数、配置及内部校验，不可只改文档就宣称接通。

## 2. Git 分片交付标准流程

1. 明确当前任务、数据版本、资产权限、仓库、目标分支和固定 commit。
2. 核对每个完整源包的大小、SHA-256 及内容范围；排除本次不允许加载的旧 checkpoint。
3. 按不超过 48 MiB 切为普通 Git 文件，记录清单版本、顺序、片数、各片长度和 SHA-256，
   同时记录每个完整文件的长度与 SHA-256。二进制不走 LFS，不做换行转换。
4. 从 GitHub 回读分支 commit 和文件 blob 哈希/长度，不能把本地 commit 或 push 返回码单独当作上传证明。
5. 在 Flux 代码拉取阶段获取分片。仓库为私有时，必须验证平台正式支持的私有 Git 授权；
   不把 GitHub token 塞进仓库 URL、普通参数、代码、公开 JSON 或日志。
6. worker 先独立校验清单 pin，拒绝 LFS pointer、缺片/多片、符号链接、不安全文件名、
   顺序/长度/哈希错误；流式拼接到新目录，不覆盖原数据；再校验整包大小与 SHA-256。
7. 安全解压并检查内部 manifest、每个数据/资产文件的哈希和结构；完成后才允许仿真初始化。
8. 镜像、依赖 ABI、入口和预算另行核实。clone 阶段并不意味着零传输或零计费，
   需要把克隆/初始化时间与 worker 运行上限、结果上传和资源释放分开记录。

### 2.1 权限边界

普通 Git 分片并不等于公开发布。原文“普通 Git 只适用于允许公开的数据”的说法过窄：
**公开仓库只放获准公开的数据；私有仓库可交付权限匹配的私有输入，但须验证 Flux 私有 clone。**

`zhu7136/1021php` 和 `zhu7136/tiangong` 都是公开仓库。用户于 2026-11-21T12:21:12Z
明确授权公开上传本次数据分片和机器人资产至 `1021php` 的新分支、不改 main，因此本次
可以沿已有公开仓库完成交付，无需新建私有仓库。此授权不包括账号密钥、签名能力或业务日志，
也不自动覆盖其他任务的数据。未获公开授权的资产仍须私有交付，不能擅自改为公开。
